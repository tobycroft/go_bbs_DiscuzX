# STB × DiscuzX 项目介绍与架构设想

> 本文档整合两个项目的现状、真实数据规模、要解决的问题，以及未来论坛架构的几种设想。
>
> - [craw_stb](https://github.com/tobycroft/craw_stb)：数据采集端（Discuz 数据抢救采集器）
> - [go_bbs_DiscuzX](https://github.com/tobycroft/go_bbs_DiscuzX) + [vue_bbs_DiscuzX](https://github.com/tobycroft/vue_bbs_DiscuzX)：论坛业务端（对标 DiscuzX）

---

## 一、项目总览

### 1.1 craw_stb（数据采集端）

**定位**：Discuz 数据抢救采集器，把源站 stboy.net 的论坛数据完整、去噪地采下来，为后续论坛业务提供数据基础。

**技术栈**：Go + Safari WebDriver（safari-crawler 桥接）+ MySQL

**四大独立模块**（`main.go` 中定义，可单独或串联运行）：

| 模块 | 命令 | 职责 |
|---|---|---|
| 板块 | `forums` | 采集论坛板块与分组（98 个板块 / 7 个分组） |
| 列表 | `lists` / `lists-full` | 采集帖子总列表（增量 / 全量重扫） |
| 详情 | `threads` | 采集主题正文与全部回复（滑动窗口并发翻页） |
| 附件 | `attachments` | 下载本站图片附件并上传 AOSS CDN |

**关键特性**：

- **断点续采**：所有任务进度落库（`crawl_thread_state` 等），异常退出后从断点继续，不重采。
- **并发 + 限速热更新**：四模块各自独立的 worker 数与请求间隔，`conf.ini` 修改后 2 秒内热生效，无需重启。
- **多标签页池**：抓取请求轮询分配到多个 Safari Tab，分摊并发、互不阻塞。
- **正文去噪清洗**：`cleaner.go` / `htmlfix.go` 对正文做噪音字符清洗、HTML 修复、水印/签名标记，产出 `content_text` 纯文本与 `content_html` 清洗后 HTML。
- **图片本地化**：`stb_image` 按 `url_hash` 全局去重，下载到本地并上传 AOSS CDN（`image.tuuz.cc`），把外链图替换为本地 CDN 地址。

### 1.2 go_bbs_DiscuzX + vue_bbs_DiscuzX（论坛业务端）

**定位**：复刻 DiscuzX 核心功能，针对千万级论坛场景做性能优化，并对搜索能力增强。

**后端技术栈**（`go_bbs_DiscuzX`）：

- Go + Gin（HTTP）+ WebSocket（`route/WsRouter.go`）
- ORM：Gorose-Pro（MySQL）
- 缓存：Redis（`tuuz/Redis`，封装 String/Hash/List/Set/SortSet/Stream/Pubsub/Rate 等）
- 自研 tuuz 框架：`common/BaseController`、`common/BaseModel`、`tuuz/*` 工具库（AES/RSA/Captcha/Mail/Date/Calc 等）

**前端技术栈**（`vue_bbs_DiscuzX`）：

- Vue 3 + Vite，前后端分离，通过 API 对接后端
- CI 自动构建 `dist` 并部署到 `fe_bbs_DiscuzX` 仓库

**项目目标**（来自 README）：复刻 DiscuzX 核心功能，**千万级论坛性能** + **搜索优化** + 安全性。

## 三、当前要解决的问题总结

### 问题 1：采集库 ≠ 论坛库

当前 `stb_*` 表是围绕「爬取 → 去噪 → 本地化」流程设计的，取舍都是为采集性能服务：

- 首帖正文塞进 `stb_thread`（宽表）、跟帖塞 `stb_reply`——采集时少一次 JOIN，但论坛业务「只看楼主 / 楼层翻页 / 引用回复 / 按用户查发帖」全都得跨两张表。
- `content_html`（mediumtext）与热字段（`title/dateline`）同表，索引体积被大字段拖累。

### 问题 2：论坛打开速度慢

| 场景 | 病根 |
|---|---|
| 板块列表页 | `WHERE fid=? ORDER BY lastpost DESC LIMIT 100000, 20`，OFFSET 深分页越翻越慢 |
| 帖子详情页 | `stb_reply` 主键是 `pid`，读一个主题的楼层是随机 IO，且缺 `fid` 索引 |
| 首页/热帖 | 每次实时聚合计数，反复扫大表 |

### 问题 3：搜索是最大痛点

- 现状：**每个用户 60 秒只能搜一次**（限流），一有用户持续搜索就「炸掉」。
- 本质：搜索是直接压在 MySQL 主库上的重查询（中文全文检索），`LIKE '%xx%'` 或 MySQL 原生 FULLTEXT 对中文分词极差，全表扫 1600 万回复，所以用限流当「保险丝」。

### 问题 4：表分区不是好方案

- 分区的唯一价值是「分区裁剪」，仅当 WHERE 命中分区键时有效；**搜索按关键词无法利用分区裁剪**。
- 分区键两难：按 `fid` 分区 → `tid` 点查跨所有区；按 `tid` 分区 → 列表页 `fid` 查询跨所有区。
- InnoDB 下分区表的优化器可用性、DDL、归档、扩容管理成本都更高。

### 问题 5：ID 冲突

源站 `uid/tid/pid/fid` 从 1 开始，未来本地注册用户也从 1 开始，直接沿用源站 ID 会冲突，必须有映射层。

### 问题 6：规模带来的结构性压力

1600 万跟帖 + 586 万图片 + 20 年跨度 + 头部单版 320 万跟帖 → 帖子表需要分表/归档策略，且绝不能对跟帖表实时 `COUNT(*)`。

### 问题 7：中文分词是搜索的核心难点

无论 MySQL 还是 PG，默认分词器对中文几乎不可用（中文无空格），必须引入中文分词方案（ngram / jieba / groonga 等）。

### 问题 8：迁移成本

`craw_stb` 的 `store.go` 大量使用 MySQL 特有语法（`ON DUPLICATE KEY UPDATE`、`NOW()`、`FOR UPDATE`、`INSERT IGNORE`），Go 侧 ORM Gorose-Pro 也是 MySQL 为主，若换数据库迁移成本较高。

## 四、几种架构设想

### 设想 A：MySQL + 独立搜索引擎（Manticore / Elasticsearch）

```
              ┌─────────────┐
   用户请求 ──▶│  Go 后端     │
              └──┬──────┬───┘
         ┌───────┘      └────────┐
         ▼                        ▼
  ┌─────────────┐          ┌──────────────┐
  │ Redis 缓存   │          │ MySQL(OLTP)  │  只做点查/短范围查
  │ 热帖/首页/计数│          │ 不搜索/不深分页│
  └─────────────┘          └──────┬───────┘
                                  │ 写后异步索引
                                  ▼
                         ┌─────────────────┐
                         │ 搜索引擎          │  承接全部搜索
                         │ Manticore / ES    │  ★ 去掉 60s 限流
                         └─────────────────┘
```

- **优点**：搜索引擎能力最强、相关性排序好、彻底解耦搜索与主库。
- **缺点**：多一个系统 + 一套索引同步管道，运维成本高。
- **选型**：Manticore（Sphinx 继承者，内置 CJK/拼音，轻量，DiscuzX 的老搭档，首选）或 Elasticsearch（功能全但重）。

### 设想 B：迁移 PostgreSQL（pgroonga / pg_bigm + 流复制从库）

- **优点**：一个数据库同时扛住 OLTP 和中文搜索，运维最简；PG 的 MVCC + GIN 抗压远强于 MySQL；声明式分区也比 MySQL 强。
- **缺点**：迁移成本高（见问题 8）；中文分词必须装扩展。
- **中文分词三选一**：
  - **pgroonga**（最推荐）：内嵌 Groonga 搜索引擎，CJK 原生，支持高亮/snippet/ranking，最接近独立搜索引擎。
  - **pg_bigm**：2-gram GIN 索引，轻量、省事、够用。
  - zhparser / pg_jieba：词法分词，精度高但需装词典，网络新词召回弱。
- **隔离搜索与点查**：主库跑写+页面点查，搜索/报表打到流复制从库，天然隔离。

### 设想 C：分层架构（采集层不动 + 论坛业务库重构）——推荐骨架

```
┌─────────────┐    ┌──────────────────┐    ┌─────────────────┐
│  craw_stb   │ →  │  source 映射层    │ →  │  bbs_* 论坛业务库 │
│ (采集层,不动) │    │ (uid/tid/pid/fid) │    │ (对标 DiscuzX)   │
└─────────────┘    └──────────────────┘    └─────────────────┘
```

- **采集层 MySQL 原样保留**，爬虫/去噪/图片本地化一条龙不改。
- **映射层**解决 ID 冲突：`bbs_source_map(source_type, source_id, local_id)`。
- **论坛业务库**按 DiscuzX 骨架重建（详见第五节），可落在 MySQL 或 PG（配合设想 A/B）。

### 设想 D：最小改动（不换数据库）

- 保留 MySQL，仅做：大字段拆 field 表 + 正确索引（`(tid, position)` 聚簇、`(fid, lastpost)`）+ 游标分页 + Redis 缓存 + 独立搜索引擎（回到设想 A）。
- **适用**：想最快见效、暂不承担换库风险时。

## 五、论坛业务库表结构设计要点（对标 DiscuzX）

DiscuzX 数据建模的四个内核，直接决定论坛能否扛住读写与扩展：

1. **主表 + field 扩展表分离**：热字段（`title/dateline`）与冷字段（`content_html` 等大字段）分表，列表页只扫瘦主表。
2. **帖子统一模型**：`bbs_post` 存所有楼层，首帖用 `first=1` 标记且 `pid == tid`，主题表只存摘要。
3. **计数器冗余**：板块/主题/用户冗余 `threads/replies/views`，读写 `+1` 更新 + 定时校准，**绝不对大表实时 COUNT**。
4. **用户多扩展表**：`member`（登录/密码/邮箱）+ `member_count`（计数）+ `member_profile`（资料大字段）分离。

### 核心表清单（bbs_ 前缀示意）

| 表 | 职责 | 关键索引 |
|---|---|---|
| `bbs_forum` | 板块（含冗余计数） | `(parent_fid)`, `(display_order)` |
| `bbs_thread` | 主题摘要（瘦表） | `(fid, lastpost)`, `(author_uid, dateline)` |
| `bbs_threadfield` | 主题正文大字段 | `tid PK` |
| `bbs_post` | 所有楼层（最大表） | **`(tid, position)` 聚簇** + `(tid, pid)` |
| `bbs_postfield` | 帖子正文大字段 | `pid PK` |
| `bbs_member` / `_count` / `_profile` | 用户三表 | `username`, `uid` |
| `bbs_attachment` | 附件/图片（承接 stb_image） | `(tid, pid)` |
| `bbs_source_map` | ID 映射层 | `(source_type, source_id)` |

### 关键设计

- `bbs_post` 用 `(tid, position)` 聚簇主键 → 读一个主题所有楼层是**顺序 IO**，替代 `stb_reply` 现在的 `pid` 主键随机 IO。
- 首帖从 `stb_thread` 迁移进 `bbs_post`（`first=1`），跟帖也进 `bbs_post`，论坛业务查询不再跨表。

### 分表 vs 分区

- **1600 万行单表 + 正确索引 + 大字段分离 + 缓存 + 搜索独立，其实完全不需要分**。
- 若未来横向扩展，用**应用层真分表**（`bbs_post_00 ~ bbs_post_63`，按 `tid % 64` 路由，单表 25 万行），路由放 Model 层一个函数里，比 MySQL 原生分区更可控、可独立归档、可继续加表。

## 六、落地路径建议

1. **先拆搜索**（收益最大、最解痛）：起 Manticore 或 PG + pgroonga，全量索引 `content_text`（纯文本字段正好喂索引），**去掉 60 秒限流**。
2. **再优化读路径**：建 `bbs_post` 用 `(tid, position)` 聚簇 + `(fid, lastpost)` 索引 + 游标分页 + Redis 缓存。
3. **再建映射层 + ETL**：采集层继续写 `stb_*`，ETL 增量同步到 `bbs_*`，两套库解耦。
4. **最后再考虑分表**：等单表真到几千万行再说。

## 七、结论（一句话）

**别在同一个数据库里同时干「点查」和「搜索」两件事。**

- 打开速度靠：**正确索引 + 游标分页 + 大字段分离 + Redis 缓存**。
- 搜索靠：**独立搜索引擎（Manticore/ES）或 PG + pgroonga + 异步索引**。
- 采集层（MySQL）原样保留，论坛业务库按 DiscuzX 骨架（瘦主表 + field 扩展 + 冗余计数 + 首帖也是 post）重建，中间用映射层衔接。

这样「表分区」和「60 秒搜索限流」这两个补丁都可以彻底扔掉。
